# Потоковая обработка больших файлов

Контрольную точку, которая не помещается в оперативную память, всё равно нужно
прочитать. `pyferrite` предоставляет чтение и запись порциями через две
рукоятки: `LazyReader` и `LazyWriter`.

Поддерживается для `.npy`, `.npz` и `.h5`. Форматы на основе pickle (`.pkl`,
`.pt`, `.joblib`) потоком обрабатывать нельзя: их полезные данные перемешаны с
графом объектов, и pickle приходится проходить с нулевого байта, чтобы понять,
где что лежит.

## Чтение

```rust,no_run
use pyferrite::prelude::*;

let opts = ReadOptions::new().chunk_elements(1 << 16);   // по 65 536 за раз
let mut r = read_lazy("huge.npy", &opts)?;

let mut running_sum = 0.0f64;
while let Some(chunk) = r.next_chunk()? {
    for x in chunk.data.as_f32().unwrap() {
        running_sum += *x as f64;
    }
}
# Ok::<(), pyferrite::Error>(())
```

### `Chunk`

| Поле | Тип | Смысл |
|---|---|---|
| `name` | `String` | Из какого массива взята порция. Для `.npy` это имя файла без расширения, для `.npz` и `.h5` — имя элемента или набора данных. |
| `dtype` | `DType` | Тип элемента после всех настроенных приведений |
| `full_shape` | `Vec<usize>` | Форма **полного** массива, а не этой порции |
| `offset` | `usize` | Плоский индекс в C-порядке, с которого начинается порция |
| `data` | `Array` | Сама порция, всегда одномерная |

Для обычной бухгалтерии есть `len()`, `total()` и `is_last()`.

Поскольку `offset` — это плоский индекс внутри `full_shape`, собрать массив
обратно просто, и так же просто решить, что нужна только часть файла:

```rust,no_run
# use pyferrite::prelude::*;
# let mut r = read_lazy("huge.npy", &ReadOptions::new())?;
while let Some(c) = r.next_chunk()? {
    let row = c.offset / c.full_shape[1];
    if row >= 1000 { break; }             // нужны только первые 1000 строк
}
# Ok::<(), pyferrite::Error>(())
```

`LazyReader` реализует также `Iterator<Item = Result<Chunk>>`, а
`collect_chunks()` соберёт всё, если вы передумали. `names()` перечисляет
массивы файла, не декодируя ни одного из них.

## Запись

Заголовок файла `.npy` предшествует данным, поэтому форма и тип элемента должны
быть объявлены до прихода первой порции:

```rust,no_run
use pyferrite::prelude::*;
use ndarray::{ArrayD, IxDyn};

let mut w = write_lazy("out.npy", DType::F32, &[100_000, 128], &WriteOptions::new())?;

for i in 0..100_000 {
    let row = Array::F32(
        ArrayD::from_shape_vec(IxDyn(&[128]), vec![i as f32; 128]).unwrap(),
    );
    w.push(&row)?;
}
w.finish()?;
# Ok::<(), pyferrite::Error>(())
```

| Метод | Поведение |
|---|---|
| `push(&Array)` | Добавляет порцию, при необходимости приводя её к объявленному `dtype`. Ошибка, если она переполнит объявленную форму. |
| `remaining()` | Сколько элементов ещё ожидается |
| `finish()` | Сбрасывает буферы и закрывает файл. **Ошибка, если пришло меньше элементов, чем объявлено**, вместо короткого файла, который выглядит корректным. |

Порции не обязаны быть одинакового размера и не обязаны совпадать по типу с
объявленным: каждая приводится на лету с учётом
`WriteOptions::cast_policy`.

## Поведение по памяти

Пиковый расход при потоковом чтении `.npy` — примерно `chunk_elements`,
умноженное на размер элемента, плюс небольшая константа. `.npz` распаковывает
по одному элементу архива, поэтому пик равен одному распакованному элементу.
HDF5 материализует по одному набору данных за раз по той же причине: индексы
чанков — это B-деревья, и чанки одного набора могут лежать где угодно в файле.

Писатель HDF5 буферизует набор данных перед его выдачей, потому что заголовки
объектов содержат адреса ещё не записанных данных. Поэтому потоковая запись
**в** HDF5 ограничивает память вызывающей стороны, но не библиотеки; если нужен
писатель с по-настоящему постоянным расходом памяти, используйте `.npy`.
