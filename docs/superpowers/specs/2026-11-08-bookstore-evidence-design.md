# 서점 근거를 분류 제안 점수에 더하기 — 설계

작성 2026-11-08. 브랜치 `feature/bookstore-score`, worktree `tm_dev-bookstore`.

## 결정 필요 (사용자 확인 전에는 구현하지 않는다)

권장안을 먼저 적었다. 승인하면 그대로 진행한다.

1. **서점 카테고리 → 내부 카테고리 대응 로직의 위치.** 이 로직은 지금 프런트엔드 JS(`frontend/src/Actions.jsx`의 `calculateCategoryScores`)에만 있다. 분류 제안은 backend 배치 작업이라 JS를 부를 수 없다.
   - **권장 (A) 이전:** 이 함수를 Rust로 옮겨 backend 한 곳에만 둔다. 동작은 바꾸지 않는다. JS 구현으로 만든 입출력 표를 Rust 테스트가 그대로 통과해야 한다. 편집 화면은 새 backend 엔드포인트를 쓰고 JS 사본은 지운다. 로직은 계속 한 벌이다.
   - (B) 사본: Rust로 옮기되 JS도 남긴다. 편집 화면 변경이 없지만 두 사본이 갈라질 위험이 있다.
   - 어느 쪽이든 새 대응 규칙은 만들지 않는다. 11-04에 지운 Python 이식 규칙(`map_category`, `bookstore_policy`)도 되살리지 않는다.
2. **서점 조회 결과 캐시.** 4,550건 제안이면 서점 요청이 수만 번이다. 다시 돌릴 때마다 반복하면 서점 차단 위험이 크다.
   - **권장:** MySQL 테이블 `bookstore_lookup_cache`에 30일 보관한다. DB 스키마 변경이라 승인 대상이다.
   - 대안: 작업 하나 안에서만 메모리에 둔다. 재실행하면 다시 조회한다.
3. **서점 조회 기본값.** 지금 프런트엔드는 `{category}`만 보내고 `use_bookstore`의 기본값은 `true`다. 서점 조회를 켜면 제안 시간이 크게 는다(아래 "비용" 참고).
   - **권장:** 제안 시작 화면에 "서점 조회" 체크박스를 두고 기본값은 끈다.
4. **가중치.** 아래 "가중치"의 초기값을 쓴다. 튜닝은 실측 뒤에 한다.

## 의도

분류 제안의 합산 점수에 서점 근거를 더한다. 서점 세 곳(yes24, 알라딘, 교보)을 독립된 판단 근거로 보고, 합의 정도에 따라 점수를 다르게 준다. 서점 점수와 모델 점수를 모두 0.0~1.0으로 정규화한 뒤 가중치로 합산한다.

## 목표

- 서점 세 곳의 결과를 각각 내부 카테고리 한 표로 바꾸고, 표가 몇 개 모였는지로 서점 점수를 정한다.
- 서점 점수와 모델 점수를 0.0~1.0으로 맞춰 기존 합산식 `score(c) = Σ w·p(c) / Σ w`에 넣는다.
- 제안 표에서 서점별 표를 확인할 수 있게 한다.

## 하지 않는 것

- 서점 검색 기능(`libs/bookstore`)을 새로 만들거나 고치지 않는다. 지금의 `BookstoreSearch::search`를 그대로 쓴다.
- 새 카테고리 대응 규칙을 만들지 않는다.
- 만화(`/comics`) 제안에는 서점 근거를 넣지 않는다. 만화는 웹툰 서점 규칙이 따로 있다.
- ISBN·키워드 근거를 없애지 않는다. 근거가 하나 늘 뿐이다.
- 가중치 튜닝은 이번 범위가 아니다.

## 실패로 보는 것 (기술적으로 돌아가도)

- 서점 차단으로 결과가 비었는데 "서점 근거 없음"이 아니라 반대 표처럼 점수를 깎는 것.
- `0_` 카테고리, 하위 디렉토리, 디스크에 없는 카테고리를 서점 근거가 추천하는 것. 지금 ISBN·키워드·모델에 걸린 거르기 규칙을 서점에도 똑같이 건다.
- 편집 화면의 서점 카테고리 추천 결과가 이번 변경으로 달라지는 것.

## 설계

### 1. 서점 한 곳의 표

파일 하나에 대해 ES 문서의 `isbn`, `title`, `author`로 서점마다 `BookstoreSearch::search`를 부른다. 세 서점은 병렬로 조회한다.

서점 한 곳의 결과(최대 4행)에서 카테고리 문자열을 모은다. 규칙은 지금 `collectStoreCategories`와 같다: 행마다 `||`로 나뉜 경로를 각각 마지막 두 단계로 줄인다. 모은 문자열마다 `calculateCategoryScores`와 같은 점수를 매겨 카테고리별로 더한다. 가장 높은 카테고리가 그 서점의 표다.

다음 경우에는 그 서점이 표를 내지 않는다(기권).

- 결과 없음, 차단(`blocked()`), 요청 오류.
- 점수가 0보다 큰 카테고리가 없음.
- 1등이 둘 이상(동점). **빌더 판단:** 억지로 고르지 않고 기권한다.
- 1등이 추천 대상이 아님: `0_` 접두, 최상위가 아님, 디스크에 디렉토리 없음.

1등이 현재 카테고리와 같으면 기권이 아니라 "제자리" 표다. ISBN 근거가 현재 카테고리를 낼 때와 같다.

대응에 쓰는 카테고리 목록은 지금 디스크의 최상위 카테고리이고, 키워드 매핑은 `category_keywords` 테이블이다. 편집 화면이 쓰는 것과 같은 출처다.

### 2. 서점 점수 (합의 정도)

표를 낸 서점 수와 관계없이 분모는 언제나 3이다. 카테고리 c의 서점 점수는 `p_bookstore(c) = c에 표를 던진 서점 수 / 3`이다.

| 상황                              | 점수                                 |
| --------------------------------- | ------------------------------------ |
| 세 곳 합의                        | c = 1.00                             |
| 두 곳 합의, 한 곳은 다른 카테고리 | c = 0.67, 다른 쪽 = 0.33             |
| 두 곳 합의, 한 곳은 기권          | c = 0.67                             |
| 세 곳 모두 다름                   | 각 0.33                              |
| 한 곳만 표를 냄                   | 0.33                                 |
| 아무도 표를 내지 않음             | 서점 근거 없음. 합산 분모에서도 뺀다 |

기권을 반대 표로 보지는 않지만, 확신은 그만큼 줄어든다. 표 수 → 점수는 상수 표 한 곳(`AGREEMENT_SCORES = [0, 1/3, 2/3, 1]`)에 둔다. 비선형으로 바꾸고 싶으면 그 표만 고친다.

### 3. 모델 점수

모델은 이미 softmax 확률을 낸다. 지금처럼 추천 대상이 아닌 카테고리를 버리고 남은 것끼리 합 1로 다시 맞춘다. 값은 0.0~1.0이다. 바꾸지 않는다.

### 4. 합산

`score(c) = Σ w·p(c) / Σ w`. 합은 그 파일에 "있음"인 근거만 더한다. 근거마다 p ≤ 1이고 한 근거 안에서 p의 합이 1 이하라서 score는 0.0~1.0이다. 서점 근거의 합이 1보다 작으면(기권이 있으면) 그만큼 점수가 낮아진다.

### 5. 가중치

**빌더 판단, 튜닝 안 함.** 순위는 ISBN > 서점 > 키워드 > 모델이다.

| 근거   | 지금 | 새 값 |
| ------ | ---- | ----- |
| ISBN   | 0.60 | 0.45  |
| 서점   | —    | 0.30  |
| 키워드 | 0.25 | 0.15  |
| 모델   | 0.15 | 0.10  |

ISBN은 같은 책의 사본이라 가장 강하다. 세 서점 합의는 외부 근거라 키워드보다 강하게 둔다.

### 6. 화면

- 후보 `source`에 `bookstore`가 더해진다. `detail`은 `"서점 0.67 · 모델 0.41"` 모양이다.
- 항목 payload에 `bookstore_votes`를 더한다. 예: `{"yes24":"3_SF","aladin":"3_SF","kyobo":null}`. 기권은 `null`이고 이유(`not_found`/`blocked`/`tie`/`excluded`)를 함께 싣는다.
- 제안 표의 점수 툴팁에 서점별 표를 보여 준다.
- 결정 3을 따르면 제안 시작 화면에 "서점 조회" 체크박스가 생긴다.

### 7. 비용과 차단

- 서점 한 곳 조회는 검색 페이지 1번과 상세 페이지 최대 4번이다. 요청마다 10초 timeout이 있다.
- 세 서점을 병렬로 부르고 파일 사이에 `delay`(기본 1.2초)를 둔다. `delay`는 서점 조회를 할 때만 쓴다. 4,550건이면 최소 약 1.5시간이다. 실제 시간은 실측으로 확인한다.
- 같은 (서점, ISBN, 제목, 저자) 조회는 캐시를 쓴다(결정 2).
- 한 서점이 연속 20번 차단되면 그 작업에서는 그 서점을 더 부르지 않는다. 제안 상태에 서점별 성공·차단·기권 수를 싣는다.

## 테스트

- 이전 로직의 동일성: JS 구현으로 만든 입출력 표(서점 카테고리 문자열, 카테고리 목록, 키워드 매핑 → 점수)를 fixture로 두고 Rust 구현이 같은 값을 내야 한다.
- 합의 점수: 위 표의 모든 행을 단위 테스트로 둔다.
- 기권: 차단·결과 없음·동점·추천 대상 아님이 각각 표가 아님을 테스트한다.
- 합산: 서점과 모델만 있을 때, 넷 모두 있을 때의 점수를 손으로 계산한 값과 비교한다.
- 서점 호출은 지금 있는 `StubStore` 대역으로 테스트한다. 실제 서점에는 붙지 않는다.
- 결정 1(A)이면 편집 화면 테스트가 새 엔드포인트로도 같은 추천 결과를 내야 한다.
