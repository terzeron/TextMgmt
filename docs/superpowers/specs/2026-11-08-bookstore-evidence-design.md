# 서점 근거를 분류 제안 점수에 더하기 — 설계

작성 2026-11-08. 브랜치 `feature/bookstore-score`, worktree `tm_dev-bookstore`.

## 결정 사항 (2026-11-08 사용자 확정)

1. **대응 로직은 backend로 옮긴다.** 프런트엔드 JS(`frontend/src/Actions.jsx`의 `calculateCategoryScores`와 helper, `Bookstore.jsx`의 카테고리 수집 규칙)를 동작 그대로 Rust로 옮긴다. 편집 화면은 새 backend 엔드포인트를 쓰고 JS 사본은 지운다. 새 대응 규칙은 만들지 않고, 11-04에 지운 Python 이식 규칙(`map_category`, `bookstore_policy`)도 되살리지 않는다.
2. **서점 검색 결과는 inode와 ISBN 두 키로 캐시한다.** inode가 ISBN보다 우선이다. 작품명을 키로 쓰는 캐시는 두지 않는다. 자세한 규칙은 설계 "2. 캐시"에 있다.
3. **서점 조회는 기본으로 켠다.** 제안 시작 화면의 "서점 조회" 체크박스는 기본값이 켜짐이다.
4. **검색어.** ISBN을 먼저 쓰고, 없으면 파일 이름에서 만든 "저자명 + 작품명"으로 검색한다.
5. **가중치**는 설계 "6. 가중치"의 초기값을 쓰고 튜닝은 실측 뒤에 한다(사용자 이의 없음).

## 의도

분류 제안의 합산 점수에 서점 근거를 더한다. 서점 세 곳(yes24, 알라딘, 교보)을 독립된 판단 근거로 보고, 합의 정도에 따라 점수를 다르게 준다. 서점 점수와 모델 점수를 모두 0.0~1.0으로 정규화한 뒤 가중치로 합산한다.

## 목표

- 서점 세 곳의 결과를 각각 내부 카테고리 한 표로 바꾸고, 표가 몇 개 모였는지로 서점 점수를 정한다.
- 서점 점수와 모델 점수를 0.0~1.0으로 맞춰 기존 합산식 `score(c) = Σ w·p(c) / Σ w`에 넣는다.
- 제안 표에서 서점별 표를 확인할 수 있게 한다.

## 하지 않는 것

- 서점 검색 기능(`libs/bookstore`)을 새로 만들거나 고치지 않는다. 지금의 `BookstoreSearch::search`를 그대로 쓴다.
- 새 카테고리 대응 규칙을 만들지 않는다.
- 만화(`/comics`) 제안에는 서점 근거를 넣지 않는다. 만화는 웹툰 서점 규칙이 따로 있다.
- ISBN·키워드 근거를 없애지 않는다. 근거가 하나 늘 뿐이다.
- 가중치 튜닝은 이번 범위가 아니다.

## 실패로 보는 것 (기술적으로 돌아가도)

- 서점 차단으로 결과가 비었는데 "서점 근거 없음"이 아니라 반대 표처럼 점수를 깎는 것.
- `0_` 카테고리, 하위 디렉토리, 디스크에 없는 카테고리를 서점 근거가 추천하는 것. 지금 ISBN·키워드·모델에 걸린 거르기 규칙을 서점에도 똑같이 건다.
- 편집 화면의 서점 카테고리 추천 결과가 이번 변경으로 달라지는 것.

## 설계

### 1. 서점 한 곳의 표

파일 하나에 대해 서점마다 검색 결과를 얻는다. 세 서점은 병렬로 조회한다. 결과는 먼저 캐시에서 찾고("2. 캐시"), 없을 때만 서점을 부른다.

검색어는 다음 순서다.

1. **ISBN.** ES 문서의 `isbn`을 하이픈을 떼고 ISBN-13으로 바꿔 쓴다. `BookstoreSearch::search(isbn, "", "")`로 ISBN 검색만 한다.
2. **저자명 + 작품명.** ISBN이 없거나 ISBN 결과가 비면, 파일 이름에서 저자명과 작품명을 만든다. 권번호·회차·완결 여부 같은 꼬리는 뗀다. 기존 가공 규칙(위 표의 "파일 이름 가공")을 쓰고 새 규칙은 만들지 않는다. `BookstoreSearch::search("", 작품명, 저자명)`을 부르면 기존 흐름이 제목+저자 → 제목 순서로 시도한다.

**빌더 판단:** 저자명은 파일 이름의 `[저자]`, `(저자)`, `제목 [저자]`, `제목 @ 저자` 표기에서 뽑는다. 기존 `stripComicDirectoryAuthor`가 떼어 내는 바로 그 부분이다. 저자 표기가 없으면 작품명만으로 검색한다.

서점 한 곳의 결과(최대 4행)에서 카테고리 문자열을 모은다. 규칙은 지금 `collectStoreCategories`와 같다: 행마다 `||`로 나뉜 경로를 각각 마지막 두 단계로 줄인다. 모은 문자열마다 `calculateCategoryScores`와 같은 점수를 매겨 카테고리별로 더한다. 가장 높은 카테고리가 그 서점의 표다.

다음 경우에는 그 서점이 표를 내지 않는다(기권).

- 결과 없음, 차단(`blocked()`), 요청 오류.
- 점수가 0보다 큰 카테고리가 없음.
- 1등이 둘 이상(동점). **빌더 판단:** 억지로 고르지 않고 기권한다.
- 1등이 추천 대상이 아님: `0_` 접두, 최상위가 아님, 디스크에 디렉토리 없음.

1등이 현재 카테고리와 같으면 기권이 아니라 "제자리" 표다. ISBN 근거가 현재 카테고리를 낼 때와 같다.

대응에 쓰는 카테고리 목록은 지금 디스크의 최상위 카테고리이고, 키워드 매핑은 `category_keywords` 테이블이다. 편집 화면이 쓰는 것과 같은 출처다.

### 2. 캐시

목적은 같은 책에 대해 서점을 다시 검색하지 않는 것이다. 키는 inode와 ISBN 둘이고, 서점마다 따로 둔다(논리적으로 inode×3, ISBN×3의 6종).

**빌더 판단:** 저장은 MySQL 테이블 두 개로 한다. 서점을 primary key에 넣어 6종을 표현한다.

**왜 ES가 아니라 MySQL인가.** 이 저장소는 이미 다음 원칙으로 둘을 나눠 쓴다. 이번 설계는 새로 나누는 것이 아니라 이 원칙을 따른다.

| 저장소 | 담는 것 | 공통점 |
|---|---|---|
| ES | 책 문서(제목, 저자, ISBN, 요약, 경로, 카테고리) | 파일을 다시 읽으면 언제든 다시 만든다. loader가 재색인한다 |
| MySQL | 카테고리 키워드, 숨김·최신 제외 카테고리, 분류 제안 항목·상태, refresh token, 열람 기록, 재적재 잠금 | 파일에서 되살릴 수 없다. 사용자 결정, 작업 상태 등 |

서점 결과는 책에 대한 정보이지만 파일이 아니라 외부 사이트 조회에서 나온다. 파일을 다시 읽어도 되살아나지 않고 서점을 다시 불러야만 되살아나므로 MySQL 쪽이다.

ES 책 문서에 함께 넣지 않는 이유도 있다. 책 문서의 `_id`가 inode라 inode 캐시 자리처럼 보이지만, 재적재가 bulk `index` 동작으로 문서 전체를 바꾼다(`libs/es_client/src/indexing.rs`). 카테고리 재적재나 파일 재색인 한 번이면 캐시가 사라진다. ES 별도 색인은 migration이 필요 없다는 장점이 있다. 하지만 ES는 OOM 장애 이력이 있고 색인이 늘면 heap 부담이 커진다. keyword 매핑을 잘못 잡으면 조용히 0건이 매칭되는 함정도 있다. 캐시를 잃으면 서점을 수만 번 다시 불러 차단 위험이 커지므로, 잘 사라지지 않는 쪽을 택한다.

| 테이블 | primary key | 값 |
|---|---|---|
| `bookstore_inode_cache` | (`inode`, `store`) | 검색 방식(`isbn`/`title_author`/`title`), 그때 쓴 검색어, 결과 행(JSON), 상태, 조회 시각, 만료 시각 |
| `bookstore_isbn_cache` | (`isbn13`, `store`) | 결과 행(JSON), 상태, 조회 시각, 만료 시각 |

**우선순위는 inode > ISBN이다.** inode는 파일이 그대로면 바뀌지 않는다. ISBN은 추출 방법에 따라 한 파일에서 여러 개가 나올 수 있어 덜 안정적이다.

조회 순서 (파일 하나, 서점 하나):

1. **inode 캐시.** 행이 있고 만료 전이면 쓴다. 단, 검색 방식이 저자명+작품명인 행은 그때 쓴 검색어가 지금 파일 이름에서 만든 검색어와 같을 때만 쓴다. 다르면(제목을 바로잡으려고 이름을 바꾼 경우) 다시 검색한다. ISBN 방식인 행은 inode를 믿고 그대로 쓴다.
2. **ISBN 캐시.** 지금 파일에 ISBN이 있으면 본다. 있으면 쓰고 inode 캐시에도 적는다. 같은 ISBN 사본끼리 결과를 나눠 쓴다.
3. **서점 검색.** 위 "검색어" 순서로 부른다. ISBN 검색 결과는 ISBN 캐시와 inode 캐시에 모두 적는다. 저자명+작품명 검색 결과는 inode 캐시에만 적는다.

저장 규칙:

- 차단·오류는 적지 않는다. 적으면 차단이 "결과 없음"으로 굳는다.
- **빌더 판단:** 결과가 있으면 만료 없이 둔다. "결과 없음"은 30일 뒤 만료해 다시 검색한다. 서점에 나중에 등록되는 책이 있기 때문이다.
- 서점 표(내부 카테고리 대응)는 캐시하지 않는다. 카테고리 목록과 키워드 매핑이 바뀌면 표도 달라져야 하므로 결과 행에서 매번 다시 계산한다.
- 파일이 지워진 뒤 같은 inode가 새 파일에 다시 쓰일 수 있다. 저자명+작품명 행은 검색어 비교로 걸러진다. ISBN 방식 행은 남을 수 있지만, 새 파일의 ISBN이 다르면 결과가 맞지 않는다. **빌더 판단:** inode 캐시 행에 그때의 ISBN도 적고, 지금 파일의 ISBN이 있는데 다르면 그 행을 쓰지 않는다. 지금 파일에 ISBN이 없으면 inode 행을 믿는다.

### 3. 서점 점수 (합의 정도)

표를 낸 서점 수와 관계없이 분모는 언제나 3이다. 카테고리 c의 서점 점수는 `p_bookstore(c) = c에 표를 던진 서점 수 / 3`이다.

| 상황                              | 점수                                 |
| --------------------------------- | ------------------------------------ |
| 세 곳 합의                        | c = 1.00                             |
| 두 곳 합의, 한 곳은 다른 카테고리 | c = 0.67, 다른 쪽 = 0.33             |
| 두 곳 합의, 한 곳은 기권          | c = 0.67                             |
| 세 곳 모두 다름                   | 각 0.33                              |
| 한 곳만 표를 냄                   | 0.33                                 |
| 아무도 표를 내지 않음             | 서점 근거 없음. 합산 분모에서도 뺀다 |

기권을 반대 표로 보지는 않지만, 확신은 그만큼 줄어든다. 표 수 → 점수는 상수 표 한 곳(`AGREEMENT_SCORES = [0, 1/3, 2/3, 1]`)에 둔다. 비선형으로 바꾸고 싶으면 그 표만 고친다.

### 4. 모델 점수

모델은 이미 softmax 확률을 낸다. 지금처럼 추천 대상이 아닌 카테고리를 버리고 남은 것끼리 합 1로 다시 맞춘다. 값은 0.0~1.0이다. 바꾸지 않는다.

### 5. 합산

`score(c) = Σ w·p(c) / Σ w`. 합은 그 파일에 "있음"인 근거만 더한다. 근거마다 p ≤ 1이고 한 근거 안에서 p의 합이 1 이하라서 score는 0.0~1.0이다. 서점 근거의 합이 1보다 작으면(기권이 있으면) 그만큼 점수가 낮아진다.

### 6. 가중치

**빌더 판단, 튜닝 안 함.** 순위는 ISBN > 서점 > 키워드 > 모델이다.

| 근거   | 지금 | 새 값 |
| ------ | ---- | ----- |
| ISBN   | 0.60 | 0.45  |
| 서점   | —    | 0.30  |
| 키워드 | 0.25 | 0.15  |
| 모델   | 0.15 | 0.10  |

ISBN은 같은 책의 사본이라 가장 강하다. 세 서점 합의는 외부 근거라 키워드보다 강하게 둔다.

### 7. 화면

- 후보 `source`에 `bookstore`가 더해진다. `detail`은 `"서점 0.67 · 모델 0.41"` 모양이다.
- 항목 payload에 `bookstore_votes`를 더한다. 예: `{"yes24":"3_SF","aladin":"3_SF","kyobo":null}`. 기권은 `null`이고 이유(`not_found`/`blocked`/`tie`/`excluded`)를 함께 싣는다.
- 제안 표의 점수 툴팁에 서점별 표를 보여 준다.
- 제안 시작 화면에 "서점 조회" 체크박스를 둔다. 기본값은 켜짐이고 요청의 `use_bookstore`로 보낸다.

### 8. 비용과 차단

- 서점 한 곳 조회는 검색 페이지 1번과 상세 페이지 최대 4번이다. 요청마다 10초 timeout이 있다.
- 세 서점을 병렬로 부르고 파일 사이에 `delay`(기본 1.2초)를 둔다. `delay`는 서점 조회를 할 때만 쓴다. 4,550건이면 최소 약 1.5시간이다. 실제 시간은 실측으로 확인한다.
- 캐시가 맞으면 서점을 부르지 않는다. 한 번 돌린 카테고리를 다시 제안하면 대부분 캐시로 끝난다.
- `delay`는 서점을 실제로 부른 파일 뒤에만 둔다. 캐시로 끝난 파일에는 두지 않는다.
- 한 서점이 연속 20번 차단되면 그 작업에서는 그 서점을 더 부르지 않는다. 제안 상태에 서점별 성공·차단·기권 수를 싣는다.

## 테스트

- 이전 로직의 동일성: JS 구현으로 만든 입출력 표(서점 카테고리 문자열, 카테고리 목록, 키워드 매핑 → 점수)를 fixture로 두고 Rust 구현이 같은 값을 내야 한다.
- 합의 점수: 위 표의 모든 행을 단위 테스트로 둔다.
- 기권: 차단·결과 없음·동점·추천 대상 아님이 각각 표가 아님을 테스트한다.
- 합산: 서점과 모델만 있을 때, 넷 모두 있을 때의 점수를 손으로 계산한 값과 비교한다.
- 서점 호출은 지금 있는 `StubStore` 대역으로 테스트한다. 실제 서점에는 붙지 않는다.
- 편집 화면 테스트가 새 엔드포인트로도 같은 추천 결과를 내야 한다.
- 캐시: inode 적중, inode 검색어 불일치로 재검색, ISBN 적중 뒤 inode 기록, inode 행의 ISBN과 지금 ISBN이 다를 때 무시, 차단 미기록, "결과 없음" 만료를 각각 테스트한다.
- 파일 이름 가공: 권번호·회차·완결 표기와 저자 표기가 있는 이름 예시로 저자명·작품명을 확인한다.

- `bookstore_votes`의 정확한 직렬화 모양.
- 연속 차단 상한 20의 조정.
